# Soft delete for chat messages on /clear and Regenerate

The user must never lose conversation history accidentally. Today the `/clear` slash command and the `Regenerate` action both **physically delete** rows from `messages`, `attachments`, and `branch_selections` — once gone, the data is unrecoverable except from a database backup. Convert those code paths to **soft delete** (set a `deleted_at` timestamp) so the rows stay in the database and can be recovered manually via SQL if needed.

Thread deletion (`DELETE /threads/:id`) keeps its current hard-delete behavior — that endpoint is an explicit "remove the whole conversation" action, not an "oh shit I cleared the wrong thread" recovery scenario.

## Requirements

### 1. Database migration

Create migration pair `028_soft_delete_messages.up.sql` / `028_soft_delete_messages.down.sql`.

**Up migration must:**
- Add `deleted_at TIMESTAMPTZ NULL` to `messages`, `attachments`, and `branch_selections`.
- Add a partial index `CREATE INDEX idx_messages_deleted_at ON messages(deleted_at)` (helps GORM's `WHERE deleted_at IS NULL` clause).
- Add the same partial index on `attachments(deleted_at)`.
- Drop the existing unique constraint `UNIQUE(thread_id, fork_message_id)` on `branch_selections` and replace it with a **partial unique index** that only applies to non-deleted rows: `CREATE UNIQUE INDEX idx_branch_thread_fork ON branch_selections(thread_id, fork_message_id) WHERE deleted_at IS NULL`. (Without this, soft-deleting a branch selection and then creating a new one for the same fork would violate the constraint.)
- Recreate the full-text-search generated column on `messages` if needed — verify the existing `tsv` column is unaffected (it is generated from `content`, so it should be fine).

**Down migration must** reverse all of the above (drop the columns, restore the original `UNIQUE` constraint).

### 2. Add GORM soft-delete fields to models

In `internal/models/message.go`, `internal/models/attachment.go`, and `internal/models/branch_selection.go`, add:

```go
DeletedAt gorm.DeletedAt `gorm:"index" json:"-"`
```

Import `"gorm.io/gorm"`. The `json:"-"` keeps the field out of API responses. GORM automatically filters `WHERE deleted_at IS NULL` for **all queries through the GORM ORM** (e.g. `db.Find(...)`, `db.First(...)`, `db.Where(...).Delete(...)`).

### 3. Convert `Regenerate` raw SQL DELETE to soft delete

In `internal/handlers/chat.go`, the `Regenerate` handler (around line 234) currently runs:

```go
h.db.Exec(`WITH RECURSIVE descendants AS (
    SELECT id FROM messages WHERE id = ? AND thread_id = ?
    UNION ALL
    SELECT m.id FROM messages m JOIN descendants d ON m.parent_id = d.id
) DELETE FROM messages WHERE id IN (SELECT id FROM descendants)`, lastMsg.ID, threadID)
```

Change to:

```go
h.db.Exec(`WITH RECURSIVE descendants AS (
    SELECT id FROM messages WHERE id = ? AND thread_id = ? AND deleted_at IS NULL
    UNION ALL
    SELECT m.id FROM messages m JOIN descendants d ON m.parent_id = d.id WHERE m.deleted_at IS NULL
) UPDATE messages SET deleted_at = NOW() WHERE id IN (SELECT id FROM descendants)`, lastMsg.ID, threadID)
```

The recursive CTE must filter by `deleted_at IS NULL` so soft-deleted ancestors don't pull live descendants into the delete set.

Also soft-delete attachments belonging to those messages — add a follow-up `UPDATE attachments SET deleted_at = NOW() WHERE message_id IN (...) AND deleted_at IS NULL` in the same handler (use a transaction so they're atomic).

### 4. Verify `ClearMessages` works through GORM auto soft-delete

In `internal/handlers/thread.go`, the `ClearMessages` handler (around line 481) uses GORM's `Delete(&models.Message{})`, `Delete(&models.Attachment{})`, `Delete(&models.BranchSelection{})`. **Once the models have `gorm.DeletedAt`, these calls automatically become soft deletes** — no code change needed. Verify this with a test (see test section).

### 5. Keep thread Delete as hard delete

In `internal/handlers/thread.go`, the `Delete` thread handler (around line 284) **must continue to physically delete** all rows. After step 2 the GORM `Delete()` calls will become soft deletes by default — switch them to hard deletes using `.Unscoped()`:

```go
tx.Unscoped().Where("thread_id = ?", id).Delete(&models.BranchSelection{})
tx.Unscoped().Where("message_id IN (SELECT id FROM messages WHERE thread_id = ?)", id).Delete(&models.Attachment{})
tx.Unscoped().Where("thread_id = ?", id).Delete(&models.Message{})
```

The thread row itself can stay as `tx.Delete(&models.Thread{}, id)` since `Thread` does not get a `DeletedAt` field in this task.

### 6. Update raw-SQL queries that read messages

GORM auto-filters `deleted_at IS NULL` only for queries built through the ORM. **Raw SQL queries via `h.db.Raw(...)` or `h.db.Exec(...)` do not auto-filter** — they must add the predicate manually.

Audit and update each of these locations to include `AND deleted_at IS NULL` (or `WHERE deleted_at IS NULL` if no existing WHERE) on the `messages` reference:

- `internal/handlers/thread.go:70` — subquery summing `cost_usd` for thread totals
- `internal/handlers/thread.go:74` — subquery in same query
- `internal/handlers/thread.go:296` — subquery in `Delete` (this one stays as-is because we want to delete attachments for ALL messages of the thread, including soft-deleted ones — but since this branch uses `.Unscoped()`, that's already handled)
- `internal/handlers/thread.go:468` — `COUNT(*) AS message_count`
- `internal/handlers/task.go:1024` — `SUM(cost_usd)` aggregate across all messages
- `internal/handlers/analytics.go:84` — `SUM(cost_usd)` since timestamp
- `internal/handlers/analytics.go:111, 152, 178, 217, 247` — analytics aggregates over messages
- `internal/handlers/search.go:79, 323` — full-text search over messages
- `internal/runner/keepalive.go:204` — `SELECT created_at FROM messages ORDER BY id DESC LIMIT 1` (last activity check)

Add `AND m.deleted_at IS NULL` (or unaliased `AND deleted_at IS NULL`) to every one. Soft-deleted messages must not contribute to cost totals, message counts, search results, analytics, or activity-based scheduling.

## Acceptance criteria

- `make check` passes (fmt + vet + lint + tests + frontend type-check).
- Manual verification via SQL: after running `/clear` in a thread, `SELECT COUNT(*) FROM messages WHERE thread_id = X` (no filter) returns the original count; with `AND deleted_at IS NULL` returns zero.
- Re-clearing the same thread multiple times works without errors.
- Creating new messages after `/clear`, then clearing again, works without unique-constraint violations on `branch_selections`.
- Thread deletion still removes all data (soft-deleted messages from prior clears must also go away with the thread).

## Implementation notes

- The full-text search `tsv` column is `GENERATED ALWAYS AS (to_tsvector('english', content)) STORED` — it is unaffected by the new column.
- The existing `Hidden` field on `Message` is unrelated — it controls UI visibility while keeping the message in conversation context. Do not conflate it with `deleted_at`.
- No restore UI is in scope. Recovery is a manual SQL operation (`UPDATE messages SET deleted_at = NULL WHERE thread_id = X AND deleted_at > NOW() - INTERVAL '1 day'`).
- No auto-purge / retention policy is in scope. Soft-deleted rows stay forever.
- Use a single migration number — pick the next one after the highest existing (currently `027_push_subscriptions`, so this should be `028_soft_delete_messages`).
