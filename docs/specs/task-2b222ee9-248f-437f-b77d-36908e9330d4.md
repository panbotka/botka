# PWA Push Frontend

Add a service worker that handles `push` events and a settings UI for the user to enable, manage, and test Web Push subscriptions.

## Context

Web Push backend already exposes these endpoints (do not modify them):

- `GET /api/v1/push/vapid-public-key` → `{"data": {"public_key": "<base64url>"}}` or 503 if push disabled.
- `POST /api/v1/push/subscriptions` body `{"endpoint": "...", "keys": {"p256dh": "...", "auth": "..."}, "user_agent": "..."}` → 201 with subscription row.
- `GET /api/v1/push/subscriptions` → `{"data": [...], "total": N}`.
- `DELETE /api/v1/push/subscriptions/:id` → 204.
- `POST /api/v1/push/test` → triggers a test push to the current user.

Botka uses `vite-plugin-pwa` (configured in `frontend/vite.config.ts`) with the workbox autogenerated service worker and `registerType: 'prompt'`. Existing in-tab notifications live in `frontend/src/hooks/useNotifications.ts` — they handle title-bar count and sound when the tab is open. This task adds Web Push that fires even when the tab is closed or backgrounded; in-tab notifications stay as-is.

## Requirements

### Service worker

- Switch VitePWA to `injectManifest` strategy in `frontend/vite.config.ts`. Source the SW from `frontend/src/sw/sw.ts`. Keep precaching (`precacheAndRoute(self.__WB_MANIFEST)`) and the existing navigateFallback behavior.
- The custom SW must:
  - Handle the `push` event:
    - Parse JSON payload `{title, body, url, tag}`.
    - Call `self.registration.showNotification(title, { body, tag, icon: '/android-chrome-192x192.png', badge: '/favicon-32x32.png', data: { url } })`.
    - If parsing fails, fall back to a generic notification (`title: "Botka", body: "New notification"`).
  - Handle the `notificationclick` event:
    - Close the notification.
    - Use `clients.matchAll({ type: 'window', includeUncontrolled: true })` to find an open Botka tab. If found, focus it and `postMessage({ type: 'navigate', url: data.url })`. Otherwise call `clients.openWindow(data.url)`.
  - Handle the `pushsubscriptionchange` event by re-subscribing using the cached VAPID public key (store it in IndexedDB or a Cache Storage entry on first subscribe so the SW can read it without network).
- The service worker must continue to precache static assets (use the workbox manifest).

### Subscription UI

- Add a "Notifications" section to `frontend/src/pages/SettingsPage.tsx`.
- Show:
  - Current state: one of "Push notifications: enabled" / "disabled" / "not supported in this browser" / "blocked by browser" / "not configured on server".
  - List of subscribed devices (from `GET /api/v1/push/subscriptions`), each row showing `user_agent` (or "Unknown device" if empty) and a remove button.
- Buttons:
  - **Enable on this device** (when supported and not subscribed): request `Notification.permission` if not granted, then call `serviceWorker.ready` → `pushManager.subscribe({ userVisibleOnly: true, applicationServerKey: <vapidUint8Array> })`, POST result to `/api/v1/push/subscriptions` with `endpoint`, `keys.p256dh`, `keys.auth`, and `navigator.userAgent`.
  - **Disable on this device** (when subscribed): unsubscribe via `subscription.unsubscribe()` and `DELETE` the matching backend row.
  - **Send test notification**: POST `/api/v1/push/test`. Show toast on success, error message on failure.
- Receive the `'navigate'` postMessage from the service worker in a top-level effect (e.g. in `App.tsx` or in `SettingsPage` if scope-limited to navigation requests) and call `react-router` `navigate(url)`.

### Hook

- Create `frontend/src/hooks/usePushSubscription.ts` exporting:
  - `state`: `'unsupported' | 'not-configured' | 'denied' | 'unsubscribed' | 'subscribed' | 'subscribing'`.
  - `devices`: array of subscriptions for the current user (from backend).
  - `vapidKey`: base64url string or null.
  - `subscribe()`, `unsubscribe()`, `removeDevice(id)`, `sendTest()`: async actions returning `Promise<void>` and surfacing errors.
  - `isSupported`: boolean (`'serviceWorker' in navigator && 'PushManager' in window && 'Notification' in window`).
- Use this hook from SettingsPage. Do not duplicate logic.

### Detection rules

- "unsupported": missing `serviceWorker`, `PushManager`, or `Notification` APIs.
- "not-configured": `GET /api/v1/push/vapid-public-key` returns 503.
- "denied": `Notification.permission === 'denied'`.
- "subscribed": current registration has a non-null `pushManager.getSubscription()` AND backend list contains a row with the same endpoint.
- "unsubscribed": supported and configured, but no active subscription.

### Coexistence with in-tab notifications

- Do not change `useNotifications.ts` — it continues to handle in-tab title-bar count and sound.
- When a push arrives while the same tab is focused, the SW still calls `showNotification`. The OS deduplicates by `tag` so the user sees one notification, not two. Document this with a one-line comment in the SW.

### Tests

- Vitest unit tests for `usePushSubscription`:
  - State transitions: unsupported, not-configured, denied, subscribe success, subscribe denied (permission denied), unsubscribe.
  - Mock `navigator.serviceWorker`, `Notification.permission`, `PushManager`, and the API client.
- Tests live in `frontend/src/hooks/usePushSubscription.test.ts`.

## Edge Cases

- iOS Safari only supports Web Push when the PWA is installed to the home screen. Detect `window.matchMedia('(display-mode: standalone)').matches` on iOS user-agents and show a hint above the Enable button: "Add Botka to your home screen first to enable push on iOS."
- User clears site data: subscription is invalidated; on next subscribe attempt, just create a new one (the backend upsert handles duplicates).
- Multiple devices per user: list all in settings, allow removing individual devices remotely (DELETE by id) — useful when a user loses a device.
- VAPID public key fetch fails (network error, not 503): show "Could not load notification settings" with retry button.

## Implementation Notes

- VAPID public key must be base64url-decoded into a `Uint8Array` before passing to `pushManager.subscribe`. Add a small `urlBase64ToUint8Array` helper in the hook.
- Switching to `injectManifest` requires updating `vite-plugin-pwa` config and may need a TypeScript include for the SW source. Follow the official `vite-plugin-pwa` `injectManifest` docs.
- Add a new API client module section in `frontend/src/api/client.ts` for push endpoints (`getVapidPublicKey`, `listPushSubscriptions`, `createPushSubscription`, `deletePushSubscription`, `sendTestPush`).
- Cache the VAPID public key in IndexedDB (or `Cache Storage`) on first successful fetch so `pushsubscriptionchange` in the SW can re-subscribe without a server round-trip.

## Out of Scope

- Backend VAPID handling, subscription storage, and push sending — already done in a prior task.
- Triggering pushes from task or chat events — wired in a separate task.
