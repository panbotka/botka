# Keepalive: schedule ping based on resets_at instead of fixed ticker

The current keepalive uses a fixed 60-minute ticker that starts when the runner starts. This is misaligned with the actual 5h rate limit window — pings fire at arbitrary times rather than just before the window expires. Replace the fixed ticker with dynamic scheduling driven by the `resets_at` value from the usage monitor.

## Requirements

- In `internal/runner/keepalive.go`, replace the fixed `time.NewTicker(interval)` in `keepaliveLoop()` with a dynamic schedule that fires the ping `KEEPALIVE_LEAD_TIME` before the current 5h window resets at (default `15m`).
- After each ping (and on initial startup), compute the next ping time as `resetsAt - leadTime`. If that's already in the past or within ~1 minute from now, ping immediately and reschedule for the next window.
- If `usageMon.ResetsAt()` returns a zero value (no usage data yet), fall back to the legacy fixed-interval behavior using `KEEPALIVE_INTERVAL` so the system still works on cold start.
- Add a new env var `KEEPALIVE_LEAD_TIME` (Go duration, default `15m`) in `internal/config/config.go`. Document in `CLAUDE.md`, `README.md`, `.env.example`.
- The `stopCh` must still cleanly stop the loop — no goroutines or timers leaked when runner stops.
- Log the next scheduled ping time on each iteration at info level (e.g. `keepalive: next ping scheduled at 2026-04-28T22:25:00Z`).
- Add unit tests covering: scheduling against a future `resetsAt`, immediate ping when `resetsAt - leadTime` is in the past, fallback to fixed interval when `resetsAt` is zero, and clean stop while waiting.

## Implementation Notes

- The Runner has access to the usage monitor via `r.usageMon`. Use `r.usageMon.ResetsAt()` to read the current reset time.
- Use `time.NewTimer` (single-fire, resettable) rather than a ticker, since the interval changes each iteration.
- Be careful with timer drift: always compute the next deadline freshly from `time.Now()` and `resetsAt` rather than chaining durations.
- This task changes scheduling only — the actual ping logic in `keepalivePing()` and `defaultPing()` stays the same.
- Coordinate with the related task "skip ping when there was recent activity" — both modify `keepalive.go` and may conflict; whoever runs second should rebase and integrate cleanly.
