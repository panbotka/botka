# Token usage and cost tracking per task

Record input/output token usage and estimated USD cost per task execution, then surface it in the UI.

## Background

Tasks vary wildly in API cost — a one-line fix vs. a multi-hour refactor differ by 100x. Today there's no per-task visibility into token consumption or money spent. The runner already parses Claude Code NDJSON events (`StreamEvent`), which contain usage data per turn.

## Requirements

- Add columns to `tasks`:
  - `input_tokens` (bigint, default 0)
  - `output_tokens` (bigint, default 0)
  - `cache_read_tokens` (bigint, default 0)
  - `cache_creation_tokens` (bigint, default 0)
  - `model` (text, nullable) — the model that actually ran (may differ from default if the user overrode)
  - `cost_usd` (numeric(10,4), default 0)
- The runner accumulates token counts from each `message_delta` / `result` event in the NDJSON stream and updates the task row when the run finishes (success OR failure — failed runs cost money too).
- `cost_usd` is computed at write time using a per-model price table (input/output/cache rates) defined in `internal/runner/pricing.go`. Pricing constants for current Claude models (Opus 4.7, Sonnet 4.6, Haiku 4.5) included; unknown model → cost left at 0 with a warning logged.
- Re-runs (retry, requeue) ADD to the existing counters — they represent total spend across all attempts, not just the latest.
- HTTP API: include the new fields in `GET /api/v1/tasks` and `GET /api/v1/tasks/:id` responses.
- New endpoint `GET /api/v1/stats/tasks?from=<date>&to=<date>&group_by=project|model|day` returning aggregated token/cost stats.
- Frontend:
  - Task detail: small panel showing tokens (split by type) and cost.
  - Task list: optional column "Cost" sortable, hidden by default behind a column toggle.
  - New "Stats" page with a stacked bar chart of daily cost grouped by project (last 30 days).
- MCP `get_task` returns the new fields.

## Implementation Notes

- Look at `internal/runner/executor.go` and `internal/claude/runner.go` for where NDJSON events are parsed; the `usage` field on assistant messages and the final `result` event both carry token counts.
- Pricing should be a small `map[string]ModelPricing` literal in code — no need for a DB-driven price table at this stage; revisit if pricing becomes dynamic.
- Do NOT block task completion on the cost calculation — if the price lookup fails, log and continue with cost=0.
- Aggregation endpoint can use a single SQL query with `date_trunc('day', completed_at)` and `SUM()` — no need to materialize a separate daily-rollup table yet.
