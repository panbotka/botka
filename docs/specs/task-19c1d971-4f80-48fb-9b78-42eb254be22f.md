# Keepalive: skip ping when usage monitor reports rate limited

When `UsageMonitor.IsRateLimited()` returns true, sending a keepalive ping either fails or just burns more tokens against an already-exceeded threshold. The ping should short-circuit in that case.

## Requirements

- In `internal/runner/keepalive.go`, modify `keepalivePing()` to call `r.usageMon.IsRateLimited()` before invoking `doPing()`. When rate limited, skip the ping and log it at info level with the reason returned by `IsRateLimited()` (e.g. `keepalive skipped: rate limited (5-hour utilization 95%)`).
- If `r.usageMon` is nil (defensive — some tests construct a Runner without one), skip the rate-limit check and proceed with the ping. Do not panic.
- Existing skip-when-stopped behavior must be preserved and take precedence (a stopped runner should still log "skipped: runner is stopped" rather than "skipped: rate limited").
- Add unit tests in `internal/runner/keepalive_test.go`:
  - Ping is skipped and `pingFn` is not called when the monitor reports rate limited.
  - Ping proceeds when the monitor reports not rate limited.
  - Ping proceeds when `r.usageMon` is nil.
- Tests should use a test-friendly way to set the usage monitor's state. The simplest approach is to construct a `UsageMonitor` directly and set `lastPollOK` and `info` fields, the same pattern used in `usage_test.go`.

## Implementation Notes

- The check is a one-liner before the existing `doPing()` call. Order: stopped check → rate-limit check → ping.
- This task is small and orthogonal to the other two keepalive tasks. Coordinate with whichever lands first to avoid merge conflicts in the same file.
