# Filter Claude Code internal [ede_diagnostic] markers out of chat error output

Stop surfacing Claude Code's internal `[ede_diagnostic]` diagnostic
markers to the user in the Botka chat UI.

## Background

Claude Code CLI adds internal diagnostic entries to the `errors` array of
its stream-json `result` event, e.g.
`[ede_diagnostic] result_type=user last_content_type=n/a stop_reason=null`.
These are internal telemetry — the CLI itself strips any entry starting with
`[ede_diagnostic]` before presenting errors. Botka currently joins the whole
`errors` array verbatim in `internal/claude/runner.go` `parseResultEvent`, so
these markers leak into chat as assistant replies.

## Requirements

- In `internal/claude/runner.go` `parseResultEvent`, drop every `result.Errors`
  entry whose trimmed text starts with `[ede_diagnostic]` before building `ErrorMsg`.
- If, after filtering, no real error text remains AND `result.Result` is empty,
  do NOT emit an error message — treat it as an empty/aborted turn (no
  `[ede_diagnostic]` string ever reaches the chat).
- Real errors (any non-`[ede_diagnostic]` entry, or a non-empty `result`) must
  still be surfaced exactly as before.
- Check the task-mode result parser (`internal/runner/parser.go`) for the same
  `errors`-array handling and apply the identical filter if present.
- Add a unit test with a `result` event whose `errors` array contains only an
  `[ede_diagnostic]` marker, asserting no diagnostic text is surfaced; and one
  mixing a marker with a real error, asserting only the real error survives.
- `make check` must pass.
