# Thread fork from message

Allow forking a thread at a specific message into a new thread, preserving all state up to that point and starting fresh from there.

## Background

Today the only way to explore an alternative direction in a conversation is to use Regenerate (which loses the original branch from the visible thread) or to manually copy/paste context into a new thread. Forking should create an independent copy of the thread state at message N, so the original thread stays untouched while the new thread can diverge.

## Requirements

- New endpoint `POST /api/v1/threads/:id/fork` with body:
  - `from_message_id` (required) — the last message to include in the fork (inclusive).
  - `new_title` (optional) — defaults to `<original title> (fork)`.
- Behavior:
  - Create a new thread with the same `project_id`, `persona_id`, `model`, `system_prompt`, `custom_context`, `folder_id` (if folders feature is in place), and tag assignments as the source.
  - Copy all messages from the source thread up to and including `from_message_id`, in order. Copy attachments rows pointing to the same underlying files (do NOT duplicate the files on disk — share by reference; bump a refcount or rely on soft-delete semantics).
  - Copy URL sources (thread_sources) from the original.
  - Do NOT copy: session ID (the new thread starts a fresh Claude session), branch_selections, soft-deleted messages.
  - The new thread's `parent_thread_id` (new column) records the source thread; `forked_from_message_id` records the fork point.
- Add columns to `threads`: `parent_thread_id` (bigint, nullable, FK self), `forked_from_message_id` (bigint, nullable, FK messages).
- HTTP API: `GET /api/v1/threads/:id` includes `parent_thread_id` and `forked_from_message_id`; `GET /api/v1/threads/:id/forks` lists threads forked FROM this one.
- Frontend:
  - Hover/right-click on any message → "Fork thread from here" action.
  - Confirmation modal showing fork point and proposed title (editable).
  - After fork, navigate to the new thread.
  - In thread sidebar / detail header, if `parent_thread_id` is set, show a small "↳ forked from <parent title>" link.
  - In source thread, show a "Forks (N)" indicator with a popover listing forked threads.
- MCP: add `fork_thread` tool with `thread_id`, `from_message_id`, `new_title`.

## Implementation Notes

- All copy operations run inside a single DB transaction so a partial fork can't be observed.
- Attachments share by reference: the new `attachments` rows point to the same file paths. Garbage collection of files (if any) must check whether ANY non-soft-deleted attachment still references the file — make sure existing GC logic does this; if not, document the new requirement explicitly in the task completion notes.
- The Claude session pool keys by thread+model — the new thread has no session id and will start a fresh subprocess on first message, which is correct.
- Cap the per-thread message count to a reasonable number (e.g. error if > 1000) to prevent runaway forks. Surface the limit in the error response.
