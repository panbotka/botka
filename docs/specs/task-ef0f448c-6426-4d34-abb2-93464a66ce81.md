# Stop the refetch storm on GET /tasks/:id/notes

An open task detail page issues `GET /api/v1/tasks/:id/notes` several times per second,
continuously, for as long as it stays open. It burns CPU on the Pi and floods the journal.

## The loop

1. `TaskNotesSection` (`frontend/src/components/TaskNotesSection.tsx:42-44`) runs
   `useEffect(() => { load() }, [load])`.
2. `load` depends on `reportCount` (line 40), which depends on the `onCountChange` prop (line 26).
3. `TaskDetailPage.tsx:376-381` passes `onCountChange` as an inline arrow literal — a new identity
   on every render.
4. On every successful fetch, `reportCount` calls `onCountChange`, whose body is
   `setTask(prev => ({ ...prev, notes_count: count }))`. The spread yields a new object even when
   the count is unchanged, so the parent re-renders, `onCountChange` is recreated, `load` is
   invalidated, and the effect fires again.

Each turn of that cycle is one HTTP request. It is self-sustaining and never settles.

## Requirements

- The notes endpoint is hit once per task-detail mount, plus once per genuine notes change
  (a note added or deleted). Not on a timer, not on unrelated re-renders.
- Break the cycle at its root: the parent must not hand the child a callback identity that changes
  every render, and must not produce new `task` state when `notes_count` has not actually changed.
  Fixing only one of the two leaves the loop one edit away from returning.
- Do not paper over it with a ref, a debounce, an eslint-disable on the dependency array, or a
  fetch-in-flight guard. Those hide the loop; they do not remove it.
- No change to `GET /api/v1/tasks/:id/notes` itself — this is entirely a frontend defect.
- The existing 5s poll of `GET /api/v1/tasks/:id` (`TaskDetailPage.tsx:133-137`) and the
  `useTaskEvents` SSE refetch are correct. Leave them alone.
