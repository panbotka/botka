# Push Notifications: Task and Chat Events

Trigger Web Push notifications when tasks fail or need review, and when a chat reply arrives. Builds on existing Web Push backend infrastructure.

## Context

Web Push backend infrastructure already exists in this repo:

- Table `push_subscriptions` with `user_id` foreign key to `users` (migration 027).
- Package `internal/push` exposing:
  - `type PushPayload struct { Title, Body, URL, Tag string }`
  - `type Sender interface { Send(ctx context.Context, userID int64, payload PushPayload) error; Broadcast(ctx context.Context, payload PushPayload) error }`
  - `func NewSender(cfg, db) (Sender, error)` — returns nil if VAPID keys missing.
- Sender is constructed at startup in `cmd/server/main.go`.

If `internal/push` does not yet expose this exact API, adapt to whatever the package provides — but do not rewrite it. Read its public surface first and use it as-is.

This task wires the Sender into existing task lifecycle and chat message creation so events fire pushes.

## Requirements

### Task event triggers

- In `internal/runner/executor.go` (and any helper that performs the final status transition), after a task transitions to `failed` or `needs_review`, send a push.
- Recipient: read the task and project models to find an owner relationship. If neither has an owner, send via `Broadcast`. Document the choice with a brief comment near the call site.
- Payload:
  - `failed`:
    - title: `"Task failed: <task title>"`
    - body: `<failure_summary>` if non-null, else first 100 chars of `failure_reason`, else `"Task execution failed"`
    - url: `/tasks/<id>`
    - tag: `task-<id>`
  - `needs_review`:
    - title: `"Task needs review: <task title>"`
    - body: `"Verification command failed"`
    - url: `/tasks/<id>`
    - tag: `task-<id>`
- No push on `done`, `cancelled`, or `running` transitions.
- Pushes are best-effort: log errors at warning level, never block or fail the task transition.

### Chat reply triggers

- In the chat message handler (search `internal/handlers/chat.go`, `internal/handlers/message.go`, and `internal/claude/runner.go` for where assistant messages are persisted), after the assistant message row is committed, send a push to the user who owns the thread.
- Title: thread title if non-empty, else `"Botka Chat"`.
- Body: first 100 chars of message content with markdown stripped to plain text (a simple regex strip is fine — remove leading `#`, list markers, code-fence markers; do not attempt full markdown parse).
- URL: `/chat/<thread_id>`.
- Tag: `thread-<id>` so subsequent replies in the same thread replace prior notifications in the OS notification centre.
- Skip the push when the thread has at least one connected SSE client for the same user (they're actively watching it). Use the existing SSE/connection registry if one exists in `internal/claude` or `internal/handlers`. If no such registry exists, send unconditionally and add a TODO comment — frontend can suppress in-tab.

### Configuration

- Add env var `PUSH_NOTIFICATIONS_ENABLED` (default `true`) to `internal/config/config.go`. When `false`, no push triggers fire from this task's wiring regardless of subscriptions.
- Document in `CLAUDE.md` Environment Variables table.

### Wiring

- Inject the Sender via constructor into the runner Executor and the chat/message handler. Do not reach into a global. Wire at app startup in `cmd/server/main.go`.
- Define a small interface in the consuming package (e.g. `runner.PushNotifier`, `handlers.PushNotifier`) with just the `Send` and `Broadcast` methods, so tests substitute a fake without depending on `internal/push` directly.
- If Sender is nil (VAPID disabled) or `PUSH_NOTIFICATIONS_ENABLED=false`, skip all push attempts cleanly.

### Tests

- Unit tests using a fake `PushNotifier` to verify `Send` is called with the correct payload on:
  - Task → failed transition
  - Task → needs_review transition
  - Task → done transition (no push expected)
  - Task → cancelled transition (no push expected)
  - Chat assistant message saved
  - Chat user message saved (no push expected)
  - `PUSH_NOTIFICATIONS_ENABLED=false` (no push expected)
- Tests should not depend on a real database connection where possible. If the existing tests for executor / chat handler use the test DB, follow the same pattern (skip when `botka_test` is unavailable).

## Edge Cases

- User has no subscriptions: `Send` returns nil, no error logged.
- Sender is nil (VAPID disabled at startup): trigger paths are no-ops without nil-pointer panics.
- Multiple rapid task failures from the same task (retry logic): stable tag (`task-<id>`) collapses notifications in the OS rather than stacking duplicates.
- Long chat message: body strictly truncated to 100 chars after markdown strip; suffix with `…` when truncated.

## Implementation Notes

- Markdown strip helper can live alongside the chat handler — keep it simple. Example transformations: strip leading `#+ `, strip leading `- `, strip ``` fences, collapse whitespace.
- Do not introduce circular imports. The `internal/push` package should not import `internal/runner` or `internal/handlers`; the dependency direction is consumers → push.
