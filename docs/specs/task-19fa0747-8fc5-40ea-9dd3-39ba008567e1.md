# Allow failed → pending status transition

Permit moving a task back to `pending` directly from `failed` status.

## Background

Currently, the task status state machine only allows transitions from `failed` to `queued` or `cancelled`. There is no way to put a failed task back into `pending` (where it sits in the backlog without being immediately picked up by the runner). Users want to triage failed tasks back to pending for later review/editing before re-queuing.

## Requirements

- Update the task status transition validation to allow `failed` → `pending` in addition to the existing `failed` → `queued` and `failed` → `cancelled`.
- The transition must be allowed via the same code path used by `update_task` (HTTP API + MCP tool).
- No side effects: moving to `pending` must NOT clear `error_message`, `failure_summary`, `attempts`, or any other failure-related fields — the user may want to inspect them.
- The runner must NOT pick up `pending` tasks (existing behavior preserved); only `queued` is eligible.
- Add or update unit tests covering the new transition and confirming previously invalid transitions remain rejected.
- Frontend: verify the task detail UI exposes a way to trigger this transition (e.g. a "Move to pending" action). If a generic status dropdown already covers it, no UI change needed; otherwise add a button/menu item next to the existing "Requeue" action.

## Implementation Notes

- Look for the status transition validation map/function in `internal/models` or `internal/handlers` (likely a `validTransitions` table keyed by current status).
- Check `internal/handlers/tasks.go` (or similar) for the `update_task` handler.
- MCP tool definition lives under `internal/mcp/`.
