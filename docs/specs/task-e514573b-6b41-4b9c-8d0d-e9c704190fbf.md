# Don't show raw "Load failed" when a live chat stream drops on reconnect

A mid-stream network drop while reconnecting to a still-live chat turn (typically iOS PWA backgrounding) surfaces the raw browser `TypeError` "Load failed" as a permanent error block with no retry; it should recover gracefully instead.

## Requirements

- On the thread mount/reconnect path (`ChatView` reconnecting via `streamSubscribe` → `GET /threads/:id/stream/subscribe`), a raw network failure of the response body read (a plain `TypeError` such as "Load failed" / "Failed to fetch", or an aborted read on resume) must NOT be rendered to the user as a permanent error block.
- Such a drop must trigger recovery, not a dead end: reconnect to the stream (with backoff), or fall back to reloading messages from the DB — mirroring how the *initial* subscribe failure is already swallowed and recovered (`ChatView.tsx:443-453`). The user must end up seeing the assistant's answer once the turn completes, without needing to wait ~10 minutes or restart the app.
- The reconnect consumption path must distinguish transient network drops from genuine backend errors. A real backend `event: error` payload should still surface (as today); only raw transport-level failures on reconnect get retried/recovered.
- No raw browser error string (`err.message` like "Load failed") may ever be rendered verbatim in `StreamErrorBlock`. If an error is genuinely shown, it must be a user-meaningful message.
- Behavior must be correct on iOS standalone PWA specifically: backgrounding then resuming a conversation whose turn is still generating must recover to the live/finished answer, not a "Load failed" block.

## Implementation Notes

- Key files: `frontend/src/components/ChatView.tsx:414-464` (reconnect effect; note `runStream` at `:442` passes no `retryStreamFn`), `frontend/src/context/SSEContext.tsx:234-276` (retry gate at `:237` only fires for `StreamError` + `connectionLost`; `:273` assigns raw `err.message`), `frontend/src/api/client.ts:813` (the `reader.read()` that throws), `:846-848`/`:969-980` (SSE parse never sets `connectionLost`; `streamSubscribe` has no retry), `frontend/src/components/StreamErrorBlock.tsx:22` (prints raw message).
- Consider treating a plain `TypeError`/abort from the reconnect stream the same as a lost connection: attempt a bounded number of resubscribes with backoff, then fall back to a DB message reload. Do not change how the *send* path reports genuine backend errors.
- Add frontend tests (Vitest) for the reconnect path: a mid-stream body read rejection must not set a visible `streamError` and must trigger recovery.
