# Investigate and fix severe mobile chat UI performance

The chat UI is smooth on desktop but extremely laggy on mobile devices
(reported on iPhone 17 Pro — a fast device, so this is a software problem,
not hardware). Diagnose the root cause(s) and fix them.

## Investigation (do this first)

- Profile the chat view on a mobile viewport (mobile Safari / small-screen
  Chrome devtools with CPU throttling). Identify what dominates: rendering,
  re-renders, layout/paint, or scripting.
- Confirm or rule out the leading hypotheses below with evidence before fixing.

## Leading hypotheses

- No message-list virtualization: `ChatView` renders every message in the
  thread at once (`messages.map`, up to ~200 messages), each through
  react-markdown + react-syntax-highlighter + rehype-highlight + KaTeX.
- `MessageBubble` has no memoization, so every ChatView state change — including
  each streaming SSE token — re-renders and re-parses markdown for ALL bubbles.
- Repaint-heavy CSS on mobile (e.g. `backdrop-blur`, large shadows, per-frame
  style/background transitions).

## Requirements

- Land a concrete fix (or set of fixes) that measurably improves mobile
  responsiveness; the fix must be justified by the profiling evidence, not
  guessed.
- Assistant messages must NOT re-parse/re-render on every streaming token for
  messages that did not change (memoize `MessageBubble` and any expensive
  markdown rendering; stable props/callbacks from `ChatView`).
- Long threads must remain responsive (scroll + typing) on a throttled mobile
  profile — introduce list virtualization or an equivalent bounded-render
  approach if profiling shows full-list rendering is the bottleneck.
- Desktop behavior, streaming, scroll-to-bottom, and existing chat features
  must remain functionally unchanged.
- Include a short before/after note in the task output: what was measured, the
  root cause, and the observed improvement.
- No visual regressions; `make check` must pass.

## Implementation Notes

- Relevant files: `frontend/src/components/ChatView.tsx`,
  `MessageBubble.tsx`, `MarkdownContent.tsx`, and the SSE streaming state that
  drives re-renders (`frontend/src/context/SSEContext`).
- Prefer memoization + virtualization over swapping out the markdown/highlight
  stack, unless profiling proves the parser itself is the dominant cost.
