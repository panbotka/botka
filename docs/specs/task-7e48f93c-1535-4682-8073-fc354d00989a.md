# Detect Claude Rate-Limit Errors and Pause Runner

Add a second runner-pause gate driven by Claude's own error responses, complementing the existing `UsageMonitor` (which polls `claude-usage` cache for 5h/7d utilization). The existing gate failed in production: it reports "under threshold" while Claude itself rejects every task with a rate-limit error.

## Why

Real incident on 2026-05-03 between 00:00 and 01:20:

- Tasks across multiple projects (e.g. botka task `2b222ee9`, memofix tasks `18d9e9db`, `b68a1476`, `254b357b`, `71003bb6`, `f6f1b10b`) ran one after another.
- Each Claude session ultimately exited with failure summary: `"You've hit your limit · resets 4:50am (Europe/Prague)"`.
- `UsageMonitor.IsRateLimited()` returned `false` the entire time (utilization showed ~12% / ~46% for the standard `five_hour` / `seven_day` buckets).
- Cumulative cost: ~$50 burned. The retry path then started a second attempt for each failed task, which exited within 400 ms with the same rate-limit error and another `failed` row.

Conclusion: `claude-usage` does not surface every quota Anthropic enforces (probably a per-model bucket like Opus weekly). The fix is to react to Claude's own error string and globally pause the runner until the reported reset time.

## Requirements

### Detect rate-limit failures

- Add a detector in `internal/runner` (e.g. `internal/runner/ratelimit.go`) with `func DetectRateLimit(failureText string) (hit bool, resetAt time.Time, ok bool)` that:
  - Returns `hit=true` when the failure summary OR raw output of a Claude execution contains any of: `"You've hit your limit"`, `"hit your usage limit"`, `"rate_limit_error"`, `"limit · resets"`. Match case-sensitively but tolerate surrounding whitespace.
  - Parses a reset time from the message, e.g. `"resets 4:50am (Europe/Prague)"` or `"resets 16:30 (UTC)"`. Use a small regex; recognise both 12-hour (`am`/`pm`) and 24-hour formats and the timezones `Europe/Prague` and `UTC`. Return the next future occurrence of that wall-clock time in the named timezone, in UTC.
  - When a reset time cannot be parsed, return `ok=false` so callers fall back to a configured cooldown.
- Unit-test the detector against fixture strings (positive + negative cases, malformed reset, missing timezone, case variants).

### Global pause gate

- Add `runner.RateLimitGate` with mutex-protected state `{pausedUntil time.Time, reason string, taskID uuid.UUID}`.
- Wire the gate into the executor's failure path (`internal/runner/executor.go` and the failure-summary generation in `internal/runner/runner.go`):
  - After a task transitions to `failed`, run `DetectRateLimit` against the failure summary and (if needed) the raw output.
  - On hit, call `gate.PauseUntil(resetAt)` (or now+cooldown if `ok=false`). Log at warn: `"runner paused until %s due to Claude rate limit (task %s)"`.
- The runner pick loop (search `pickNextTask` / `collectTickState`) must check the gate alongside `UsageMonitor.IsRateLimited()` and skip launching when `time.Now().Before(gate.PausedUntil())`.
- Persist the gate across restarts: store `paused_until` and `pause_reason` in a new row of the existing `setting` table (key e.g. `runner_rate_limit_pause`) — load on startup, write on every change. Do NOT add a new migration unless the table doesn't exist; reuse the existing app-settings storage.
- The currently-running task is allowed to finish; only future launches are blocked.

### Don't retry into the wall

- The existing one-shot retry (the second `Attempt` row observed in the incident) must check the rate-limit gate before being scheduled. If the gate is active, the task stays in `failed`, `retry_count` is NOT incremented, and the retry runs after the gate clears.
- Tasks queued during the pause stay `queued` and are picked up after the gate clears (no special handling needed beyond the pick-loop check).

### Status surfacing

- Extend `GET /api/v1/runner/status` response with `paused_until` (ISO8601 string or null), `pause_reason` (string or null), `pause_source` (`"rate_limit"` for now; future-proof for other sources).
- Mirror the new fields in the runner status MCP tool (`internal/mcp/...`).
- Update the frontend RunnerStatus component (search `frontend/src/components/RunnerStatus.tsx`) to show a yellow banner when paused: `"Runner paused until <local time> — Claude rate limit"`. Banner disappears automatically once `paused_until` is in the past (driven by a 30s tick already present, or add one).

### Manual override

- Add `POST /api/v1/runner/clear-rate-limit` (auth: same as other runner control endpoints). Clears the gate immediately and returns 204.
- Add a "Clear pause" button to the RunnerStatus banner that calls this endpoint.

### Configuration

- Add env vars to `internal/config/config.go`:
  - `CLAUDE_RATE_LIMIT_COOLDOWN` (default `2h`, Go duration) — used when reset time cannot be parsed from Claude's message.
  - `RATE_LIMIT_DETECTION_ENABLED` (default `true`) — when false, the detector is bypassed and only the existing `UsageMonitor` gate applies.
- Document both in `CLAUDE.md` Environment Variables table.

### Tests

- Unit tests for the detector covering each known signal phrase, both timezones, both 12-hour and 24-hour formats, malformed reset (fallback path), and the negative case (a normal failure with no rate-limit text).
- Unit tests for `RateLimitGate`: pause persists, expires automatically when `pausedUntil` passes, manual clear works, persists across reload from `setting` table.
- Unit tests for the runner pick loop: when gate is active, no task is launched even if `UsageMonitor` says OK.
- Handler integration test for `GET /api/v1/runner/status` (verifies the new fields when paused / not paused) and `POST /api/v1/runner/clear-rate-limit`.

## Edge Cases

- Multiple tasks fail with rate-limit errors back-to-back (race during the brief window before the gate is set): use `gate.PauseUntil` semantics that take the MAX of existing and new pausedUntil so a later, longer pause from a different task isn't shortened.
- The reset time parsed from Claude's message is in local TZ (`Europe/Prague`) but the server may run in UTC. Use Go's `time.LoadLocation("Europe/Prague")` and convert to UTC for storage. Test both with `TZ=UTC` and `TZ=Europe/Prague`.
- If the parsed reset time is already in the past (clock skew), use `now + 5min` as a minimum to avoid an immediate retry storm.
- The detector text matches a substring inside Claude's longer failure summary; do not require exact equality.

## Out of Scope

- Rewriting `UsageMonitor` or `claude-usage`. The new gate is additive — both gates run, runner is paused if either says so.
- Predicting per-model quotas in advance. We react to Claude's actual errors.
- Auto-resuming individual failed tasks after pause clears. Existing scheduler picks them up naturally; no extra logic.

## Acceptance

- After this task lands, replaying the 2026-05-03 incident scenario (Claude returns `"You've hit your limit · resets <time>"`) results in: first task fails, runner pauses, no further tasks launch, banner appears in UI, gate auto-clears at the reset time.
- $50 burn from last night does not repeat.
